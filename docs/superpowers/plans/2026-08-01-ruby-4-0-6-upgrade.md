# Ruby 4.0.6 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the app from Ruby 3.4.7 to 4.0.6 in an isolated git worktree, with `bin/rails test` and `bundle exec standardrb` green, without disturbing any other agent working in `~/dev/the-greatest`.

**Architecture:** All work happens in the existing worktree `~/dev/the-greatest-ruby4` on branch `ruby-4-0-6` (already rebased onto `main` at `66612b6`). Ruby is pinned per-worktree by an untracked `mise.toml` in the worktree root, which beats `~/dev/mise.toml` on mise's nearest-config-first resolution. The repo diff is tiny — two version pins and a lockfile. Nearly all the work is triaging native-extension gems that have no Ruby 4.0 build.

**Tech Stack:** Ruby 4.0.6, Rails 8.1.3.1, mise, Bundler 4.x, Minitest, standardrb, PostgreSQL on `localhost:6543`.

**Spec:** `docs/superpowers/specs/2026-08-01-ruby-4-0-6-upgrade-design.md`

## Global Constraints

Every task's requirements implicitly include this section.

- **Ruby target is exactly `4.0.6`.** Not `4.0`, not `latest`.
- **Work only inside `/home/shane/dev/the-greatest-ruby4`.** Never edit files in `/home/shane/dev/the-greatest` — another agent works there.
- **Never edit `~/dev/mise.toml`.** It pins Ruby for the entire `~/dev` tree; changing it switches every other worktree to a Ruby with no gems installed.
- **Gem policy: bump blockers only.** Only gems that actively prevent `bundle install` or the suite from working, each to the *minimum* version that works. No opportunistic `bundle update`. Record every bump — the final report must list them.
- **Never run `db:test:prepare`, `db:drop`, `db:reset`, or `db:schema:load`.** The test database is shared with other worktrees. A `PreToolUse` hook blocks most of these anyway.
- **Never touch `the_greatest_development`.** The books data exists only in dev and takes hours to rebuild.
- **Linter is `bundle exec standardrb`**, never `bin/rubocop`. Do not run brakeman.
- **Do not run** system tests, Playwright E2E, `yarn install`, or a Docker build. Out of scope.
- **Commit freely on `ruby-4-0-6`. Do not push and do not open a PR** without asking.
- All Rails commands run from `web-app/`.
- **Every Ruby-touching command MUST be prefixed with `mise exec --`.** Not optional, not
  cosmetic. A shell that starts outside the worktree and `cd`s in keeps a PATH baked to
  Ruby 3.4.7 — mise's `chpwd` hook does not re-fire inside a compound command. Verified
  contrast in this very worktree:

  | invocation | ruby | bundler | GEM_HOME |
  |---|---|---|---|
  | `mise exec -- …` | 4.0.6 | 4.0.16 | `…/ruby/4.0.6/…` |
  | bare | 3.4.7 | 2.6.2 | `…/ruby/3.4.7/…` |

  A bare `bundle install` or `bin/rails test` silently runs the **old** Ruby and produces
  a false green for the entire upgrade. This is the single easiest way to waste the whole
  effort.

### Task 2: Pin Ruby 4.0.6 to this worktree only

`mise` resolves nearest-config-first. A `mise.toml` in the worktree root beats `~/dev/mise.toml` inside this directory tree and is invisible outside it. A *global* mise setting cannot do this job — `~/dev/mise.toml` is nearer than `~/.config/mise/config.toml` and overrides it for everything under `~/dev`.

**Files:**
- Create (untracked): `mise.toml` in the worktree root
- Modify: `.git/info/exclude`

**Interfaces:**
- Produces: `mise exec -- ruby -v` reporting `4.0.6` inside the worktree; every later task depends on this.

- [ ] **Step 1: Confirm Ruby 4.0.6 is installed**

```bash
mise ls ruby
```

Expected: `4.0.6` appears in the list. It was installed on 2026-08-01, so no compile is needed. If it is missing, run `mise install ruby@4.0.6` (a from-source build; expect 5–10 minutes).

If that build fails demanding Rust 1.85+, it is attempting ZJIT. ZJIT is experimental in 4.0 and the Ruby team advises against production use, so build without it (`--disable-zjit` via `MISE_RUBY_CONFIGURE_OPTS`) rather than installing a Rust toolchain. This is a build-time concern only; nothing at runtime depends on it.

- [ ] **Step 2: Exclude `mise.toml` from git before creating it**

`info/exclude` lives in the shared common git dir, so this entry is also visible to the main repo. It is inert there — `~/dev/the-greatest` has no `mise.toml` — but be aware it is shared state.

```bash
cd /home/shane/dev/the-greatest-ruby4
```

- [ ] **Step 3: Write the worktree-local mise config**

Create `/home/shane/dev/the-greatest-ruby4/mise.toml`. `node` is pinned to the identical value in `~/dev/mise.toml` so nothing except Ruby shifts:

```toml
[tools]

ruby = "4.0.6"
```

- [ ] **Step 4: Verify the worktree now resolves 4.0.6**

```bash

mise current ruby                 # config resolution
mise exec -- ruby -v              # what commands will ACTUALLY run
mise exec -- gem env home         # must be a 4.0.6 path
```

Expected: `4.0.6`; `ruby 4.0.6`; and a GEM_HOME under `…/installs/ruby/4.0.6/…`.

**This is the load-bearing check of the whole plan.** If any of the three disagrees, stop and diagnose rather than proceeding, or you will bundle and test under 3.4.7 and believe a false green.

All three checks are needed, because they can disagree. `mise current` only proves the *config* resolves to 4.0.6; it says nothing about the PATH a command will actually inherit. A bare `ruby -v` here is actively misleading — it reports **3.4.7** even when the pin is correct, because the shell's PATH was baked before the `cd`. That is why every Ruby-touching command in this plan carries the `mise exec --` prefix. `gem env home` is the tiebreaker: it proves gems will install into the 4.0.6 tree rather than clobbering 3.4.7's.

- [ ] **Step 3: Triage a blocker (repeat per blocking gem)**

Match the failure to its shape:

| Failure | Meaning | Fix |
|---|---|---|
| `<gem> requires ruby version >= X`, or a resolution conflict naming a gem | gemspec caps Ruby below 4.0 | `bundle update <gem> --conservative` |
| Native compile errors (`make failed`, missing header, ABI errors) | no precompiled 4.0 binary; source build failing | `bundle update <gem> --conservative` |
| `Could not find <gem>-<version> ... in locally installed gems` | locked version has no artifact for this Ruby | `bundle update <gem> --conservative` |

`--conservative` is what keeps the change minimal — it moves the named gem without dragging its dependencies forward. **Bump one gem at a time and re-run `bundle install`**, so each bump is attributable. Do not run a bare `bundle update`.

If a gem cannot be resolved at any version, STOP and report — that is a genuine blocker, not something to work around.

## Notes for the implementer

**The single most important check** is Task 2 Step 4 — and it has two independent failure modes, both observed here for real.

*Config resolution.* With 4.0.6 installed but no worktree-local config, the worktree resolved 3.4.7, because `~/dev/mise.toml` is nearer than the global mise config. Setting Ruby globally cannot fix this.

*PATH staleness.* Even with the config correct, a shell that starts outside the worktree and `cd`s in keeps a PATH pointing at Ruby 3.4.7 — mise's `chpwd` hook does not re-fire inside a compound command. `mise current ruby` says `4.0.6` while `ruby -v` says `3.4.7` and `which ruby` points into `installs/ruby/3.4.7/bin`. **This one is nastier than the first, because the check passes while the toolchain is wrong.** Hence `mise exec --` on every Ruby-touching command and `gem env home` as the tiebreaker.

**The test database is shared.** A worktree isolates files, gems, and toolchain — not Postgres. Every worktree resolves `database.yml` to the same `the_greatest_test`, and `parallelize(workers: :number_of_processors)` fans it out to `the_greatest_test-0..N`. Hence the concurrency guard before every suite run and the rule to re-run before believing red.

The guard uses `grep "[b]in/rails test"` rather than `pgrep -af "rails test"`. The bracket
prevents the pattern from matching the guard's own command line — plain `pgrep` self-matches
here and reports BUSY every time, which trains you to ignore it.
