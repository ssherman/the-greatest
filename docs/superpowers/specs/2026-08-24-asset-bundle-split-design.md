# Asset bundle split — design

**Date:** 2026-08-24
**Status:** Approved, ready for implementation planning
**Worktree:** `/home/shane/dev/the-greatest/.claude/worktrees/asset-bundle-split` (branch `worktree-asset-bundle-split`)

## Problem

Every layout — `books`, `music`, `games`, and `admin` — loads the same
`javascript_include_tag "application"`. Rollup builds per-domain bundles on every
`yarn build`, and no layout references any of them. The domain bundles are also
wrong: `books.js` and `music.js` never `import "./controllers"`, so had anything
ever loaded them, zero Stimulus controllers would have registered.

The shared bundle has no minifier. A public page downloads **184 KB gzipped**
(889 KB raw), including the entire admin controller set and the Firebase auth SDK.

## Measurements

All figures are minified + gzipped — what a browser actually transfers. Measured
against the current build on 2026-08-24.

Current shared bundle, decomposed:

| Piece | min+gzip |
|---|---|
| Turbo (`turbo-rails`, incl. ActionCable) | 28.3 KB |
| Firebase auth SDK | 32.3 KB |
| Stimulus runtime | 9.3 KB |
| 24 controllers + autocomplete.js + services | ~19.6 KB |
| **Total after minification** | **89.5 KB** |
| **Total as shipped today (unminified)** | **183.9 KB** |

Projected public-page payload after each increment:

| After | min+gzip | Delta |
|---|---|---|
| Today | 184 KB | — |
| 1. Minify | 89 KB | −95 KB |
| 2. Split into 4 bundles | ~85 KB | −4 KB |
| 3. Drop ActionCable | ~81 KB | −3.5 KB |
| 4. Firebase on demand | ~49 KB | −32 KB |

**Increments 1–3 deliver 70% of the total win without touching authentication.**

Rejected on measurement: splitting domain CSS into web/admin variants by excluding
`app/views/admin/**` and `app/components/admin/**` from Tailwind's `@source` globs
saves **1.75 KB gzip** (28.1 → 26.4). Not worth doubling the CSS build matrix. CSS
stays at one file per domain.

## Constraint: Propshaft cannot rewrite ES import specifiers

Propshaft 1.3.2's `Propshaft::Compiler::JsAssetUrls` rewrites only explicit
`RAILS_ASSET_URL(...)` markers. It does not touch `import` statements. A rollup
shared chunk referenced as `./chunk-abc.js` from a digest-stamped parent resolves
to `/assets/chunk-abc.js` — undigested, 404.

Therefore: **self-contained IIFE outputs, no shared chunks.** This costs nothing.
The three sites are separate hostnames with separate HTTP caches, so a shared
vendor chunk would never actually be shared between them.

The same constraint rules out `import()` for lazy Firebase, which is why Firebase
becomes its own entry loaded by an injected `<script src>` (see below).

## Architecture

### Bundles

Rollup config becomes a data-driven `BUNDLES` list, one entry per output. End state
after all four increments:

| Output | Loaded by |
|---|---|
| `<domain>-web.js` | that domain's layout — one per `app/views/layouts/*/application.html.erb` |
| `admin.js` | `layouts/admin.html.erb` (all hostnames) |
| `firebase-auth.js` | nothing — injected at runtime (arrives in increment 4) |

**The web entries are derived from the domain layouts that exist, not hand-listed.**
Propshaft raises `Propshaft::MissingAssetError` on a missing asset, so a layout
referencing a bundle that was never built is a hard page failure across that whole
site. A layout must never be able to name a bundle the build does not produce — see
the coverage guard under Testing.

Web is split per domain because the domains genuinely differ and separate
hostnames mean per-domain bundles cost nothing. Admin is **one** bundle: it lives
at `/admin` on each domain's own hostname, and there is zero domain-specific admin
JavaScript, so three admin bundles would be byte-identical. If domain-specific
admin code ever appears, splitting is a line in the `BUNDLES` list.

All outputs keep `format: "iife"` and `sourcemap: true`.

### Controller manifests

The root cause of "nothing tree-shakes" is that `controllers/index.js`
(auto-generated by `stimulus:manifest:update`) imports all 24 controllers, and
every entry does `import "./controllers"`. Replace it with explicit per-bundle
manifests under `app/javascript/manifests/`:

- **`web_shared.js`** — `authentication`, `autocomplete`, `membership-state`,
  `toast`, `reviews--modal`, `reviews--my-reviews`, `reviews--spoiler`,
  `reviews--widget`, `user-list-add-item`, `user-list-modal`, `user-list-state`,
  `user-list-widget`
- **`books_web.js`** — web_shared + `books--filter`, `saved-search-picker`
- **`music_web.js`** — web_shared + `year-range-modal`
- **`games_web.js`** — web_shared + `year-range-modal`
- **`admin.js`** — `admin--markdown-preview`, `admin--search`, `autocomplete`,
  `auto-dismiss`, `clipboard-copy`, `conditional-field`, `metadata-editor`,
  `modal-form`, `review-filter`, `reviews--spoiler`, `shared-modal`, `wizard-step`

`bin/rails stimulus:manifest:update` is retired for this app; `controllers/index.js`
is deleted.

### Drift guard

Hand-split manifests recreate the failure already present in the codebase:
`auto-dismiss` is referenced by three admin views and registered nowhere, so admin
flash messages have silently never auto-dismissed.

**Correction, made during implementation.** This spec originally also called
`conditional-field`, `metadata-editor` and `modal-form` dead and had them deleted.
That was wrong, and the mistake is instructive enough to keep on the record: they are
**live admin-only controllers**, reached through Rails' tag-builder hash idiom —
`data: { controller: "metadata-editor modal-form" }` — in 2, 4 and 47 files
respectively. That form renders to `data-controller="…"` at runtime but never appears
as that literal string in source, so a scan of the attribute alone reported them as
referenced by nothing. They were deleted on that evidence and restored when a review
caught it.

The guard therefore scans **both idioms** — the literal `data-controller="…"`
attribute and `controller: "…"` inside a Rails `data:` hash — skipping tokens
containing `/` so `url_for(controller: "admin/games")` cannot register a phantom. It
also strips comments before scanning registrations, so a commented-out
`application.register(…)` no longer counts as registered.

A new `test/lint/stimulus_manifest_test.rb` — alongside the three lint tests already
in `test/lint/` — scans `app/views/**` and `app/components/**` for both idioms and
enforces five rules, all decidable from the file tree with no guessing about render
sites:

1. Referenced anywhere ⇒ present in at least one manifest
2. Present in a manifest ⇒ referenced somewhere
3. Referenced **only** under an `admin/` path ⇒ absent from all web manifests
4. Referenced from a shared path (`reviews/`, `user_lists/`, `layouts/`, root-level
   components) ⇒ present in all three web manifests
5. Referenced from `views/<domain>/` or `components/<domain>/` ⇒ present in that
   domain's web manifest

**Manifest membership resolves transitively.** `books_web.js` imports `web_shared.js`,
so a controller registered in `web_shared` counts as present in all three web
manifests for rules 3–5. The test must follow the import graph, not read each
manifest file in isolation.

Rule 1 would have caught `auto-dismiss`. Rule 2 is the one that misfired on the
three live controllers above until the scanner learned the second idiom — a guard is
only as good as its notion of "referenced". The allowlist is empty and should stay
that way; when the test fails, fix the manifest.

Note rule 4's necessity: `AutocompleteComponent` lives at
`app/components/autocomplete_component.rb` (root, not admin) but is rendered by both
admin views and `user_lists/show/add_item_component`. A path heuristic alone would
mis-assign it.

### Layout wiring

A `domain_js_bundle` helper in `DomainHelper` returns `"#{current_domain}-web"`.
Domain layouts call it; `layouts/admin.html.erb` hardcodes `"admin"`.

This also fixes `app/views/layouts/application.html.erb`, which references
`#{current_domain}/application` for both JS and CSS — paths that have never existed.
Nothing sets this layout explicitly, but it is Rails' default fallback, so it is a
production 500 waiting for any controller that omits a `layout` declaration.
Propshaft raises `Propshaft::MissingAssetError` on a missing asset.

### Firebase on demand

New entry `app/javascript/firebase_bundle.js` → IIFE exposing
`window.__tgFirebase = { firebaseAuthService, googleProvider, emailProvider, redirectHandler }`.

`authentication_controller.js` drops its four static imports and gains a
`loadFirebase()` that injects a `<script src>` once. The URL comes from Rails via a
Stimulus value on the widget element:
`data-authentication-firebase-src-value="<%= asset_path('firebase-auth.js') %>"`.

**The load promise is memoized at module scope, not on the controller instance.**
Turbo caches mutated DOM and re-runs `connect()` on restore, so instance-level
memoization would re-inject the script on every Back navigation.

**All Firebase access goes through a single `await this.firebase()` accessor.** The
module-level singletons are never referenced directly anywhere in the controller.
This is the structural mitigation for the main risk: in an async refactor of a
controller that currently does everything synchronously in `connect()`, a missed
`await` yields `undefined` and fails silently. Routing every touch through one
accessor makes a missed `await` a visible mistake.

Firebase **eager-loads** on `connect()` when **any** of these is present:

- The **`tg_uid` cookie** — the app's existing signed-in marker, set by
  `AuthController` (`TG_UID_COOKIE`) on sign-in, deleted on sign-out, backfilled by
  `/user_list_state`, and cleared on a 401. Four controllers already gate on it
  (`user_list_state`, `membership_state`, `user_list_widget`, `reviews/widget`), each
  with its own copy of the same three-line regex; the auth controller adds a fifth,
  matching the established convention rather than introducing a shared module used by
  one of five call sites.
- `localStorage['tg:auth:signed-in']` — set on successful sign-in, cleared on
  sign-out.
- `sessionStorage['tg:auth:pending-redirect']` — set immediately before
  `signInWithRedirect`, cleared once `getRedirectResult` resolves. As belt-and-braces
  the check also matches any existing `firebase:pendingRedirect*` sessionStorage key.

Otherwise Firebase loads only when the user opens the login modal.

**Why both `tg_uid` and the localStorage flag, rather than either alone.** They fail
in opposite directions and the union is strictly safer than either:

- `tg_uid` is a **session** cookie with no explicit expiry, so it dies on browser
  restart. Firebase's own persistence is IndexedDB, which survives. Gating on
  `tg_uid` alone would show "Login" to a still-signed-in user after every browser
  restart — a visible regression.
- The localStorage flag is persistent and survives restarts, but is a client-side
  mirror that can drift (a sign-out in another tab does not clear it in tabs that
  never loaded Firebase). `tg_uid` is server-managed and authoritative.

A false positive is cheap — load Firebase, get a null user, clear the flag, render
Login. A false negative is the visible regression. So the condition is a union, and
any hint of a signed-in user triggers the eager load.

**Why an eager-load signal is required at all.** Without one, a returning signed-in
user's navbar would sit on "Login" until they clicked something: only Firebase knows
they are signed in, and the page is edge-cached so the server cannot render it. This
preserves current behavior — signed-in users still pay the 32 KB, anonymous readers,
the overwhelming majority of traffic, do not.

Note that `data-signed-in="<%= signed_in? %>"` on the domain layouts' `<body>` is
**not** a usable signal: those pages are edge-cached via `Cacheable`, so the baked-in
value reflects whoever first populated the cache. That is precisely why `tg_uid` and
client-side hydration exist.

Failure modes, all graceful:

| Situation | Result |
|---|---|
| Signal present, Firebase session expired | Loads Firebase, gets null user, clears flag, renders Login. Correct. |
| Browser restarted (`tg_uid` gone) | localStorage flag still set → eager load. Correct. |
| localStorage flag stale after sign-out in another tab | `tg_uid` already deleted, but the stale flag still triggers a load → null user → flag cleared. Correct, at the cost of one download. |
| Both signals absent, Firebase session live | Sees Login until they click; clicking restores the session. Degraded, not broken. |
| Storage blocked entirely | `tg_uid` alone still covers the common case within a browser session. |
| sessionStorage lost across the redirect | Firebase's own `firebase:pendingRedirect:*` key has the identical durability requirement, so this path is already broken today. No new failure mode. |

**CSP:** `config/initializers/content_security_policy.rb` is entirely commented out,
so nothing blocks the injected tag. If a policy is added later, the script is
same-origin `/assets/…`, which plain `script-src 'self'` covers — no nonce needed for
an external `src`.

**Edge-cache staleness:** `asset_path` bakes a digest into cached HTML, so cached
pages can reference a digest removed by a later deploy. This is the same staleness
profile the existing `javascript_include_tag` already has — the same risk class, not
a new one.

**Rollback:** if on-demand loading misbehaves, changing the eager-load condition to
unconditional `true` restores today's exact behavior in one line, keeping the split
and minification intact. Backing out does not require reverting anything.

### Drop ActionCable

`@hotwired/turbo-rails`'s JS entry imports `cable_stream_source_element` and `cable`,
pulling ActionCable into every page for 3.5 KB gzip.

Verified unused: zero occurrences of `turbo_stream_from`, `broadcasts_to`, or any
`broadcast_*` helper in `app/`, `config/`, or `test/`, and no `app/channels`
directory. `<turbo-cable-stream-source>` is the only thing that opens a cable
connection, and it only enters the DOM via `turbo_stream_from`.

Turbo Frames are plain `fetch` and never involve ActionCable. Turbo Stream
*responses* over HTTP (`text/vnd.turbo-stream.html`, used by 8+ controllers
including `reviews_controller` and `list_items_actions`) are core Turbo and equally
unaffected.

Replace `import "@hotwired/turbo-rails"` with a small local shim that imports
`@hotwired/turbo`, sets `window.Turbo`, and re-adds the one Rails-specific piece that
matters:

```js
import { encodeMethodIntoRequestBody } from "@hotwired/turbo-rails/app/javascript/turbo/fetch_requests"
addEventListener("turbo:before-fetch-request", encodeMethodIntoRequestBody)
```

`encodeMethodIntoRequestBody` encodes `_method` into non-GET form bodies. Without it,
`form_with method: :patch` and `button_to method: :delete` silently degrade to POST.
The deep import is a coupling to turbo-rails' internal path and must be re-checked on
every turbo-rails upgrade; the shim lives in one file with a comment saying so.

## Cleanup carried by this work

- Remove `application.debug = true` and the two `console.log`s from
  `controllers/application.js` — they ship Stimulus debug logging to production
  readers today. `window.Stimulus` stays as a debug handle.
- Delete `conditional_field_controller.js`, `metadata_editor_controller.js`,
  `modal_form_controller.js` — registered, referenced by nothing. Drift-guard rule 2
  fails otherwise.
- Write the missing `auto_dismiss_controller.js` (~15 lines) and register it in the
  admin manifest. Three admin views have expected auto-dismissing flash since they
  were written. Drift-guard rule 1 fails otherwise. (The tighter-scope alternative —
  removing the three `data-controller` attributes — was considered and rejected: the
  views clearly intended the behavior.)
- Sourcemaps stay enabled. They become *more* valuable once output is minified, and
  browsers fetch them only when devtools is open.

Not acted on: `admin/news_posts_base_controller.rb:116` documents a design choice
constrained by this problem ("A client-side Markdown library is not an option while
admin and public share application.js"). That constraint lifts, but the comment gives
a second, better reason to keep the preview server-rendered — it cannot drift from
`BodyRenderer`. Preview behavior is unchanged.

## Testing

- Integration assertions that each layout requests its own bundle. Assert the script
  `src` path, not markup — behavior, not copy.
- **Bundle coverage guard.** For every `app/views/layouts/*/application.html.erb` plus
  `layouts/admin.html.erb` and `layouts/application.html.erb`, assert the bundle name
  the layout resolves to is produced by the rollup `BUNDLES` list. A layout naming an
  unbuilt bundle is a `Propshaft::MissingAssetError` — a 500 on every page of that
  site, discovered in production. This is the single highest-consequence failure mode
  in the whole change and the cheapest to guard.
- `test/lint/stimulus_manifest_test.rb`, the drift guard.
- Playwright E2E: sign-in on all three public sites plus admin. This is the genuinely
  risky surface. CI does not run Playwright, so this is a local pre-merge gate.
- Record before/after gzip sizes per bundle and confirm against the projections above.

Standard gates apply: `bin/rails test` and `bundle exec standardrb` must be green
before merge.

## Increments

Ordered so the risky change is last and fully droppable.

1. **Minify + kill debug logging.** `@rollup/plugin-terser` on all entries. Biggest
   single win, near-zero risk. Verify sizes.
2. **Split web from admin.** One bundle per domain layout plus `admin` — no
   `firebase-auth` yet, that arrives in increment 4. Manifests, `domain_js_bundle`
   helper, layout wiring, drift-guard test, bundle coverage guard, dead-controller
   cleanup, `auto_dismiss_controller`. The old `application.js` entry is removed only
   once every layout has been repointed and the coverage guard is green.
3. **Drop ActionCable.** The turbo shim. Isolated so it can be dropped.
4. **Firebase on demand.** Separate entry, injected script, both eager-load flags,
   E2E across all four sign-in surfaces.

Each is independently shippable.

## Out of scope

- Splitting CSS into web/admin variants — measured at 1.75 KB gzip.
- Changing news post preview rendering.
- Any change to `Services::News::BodyRenderer` or the auth service layer beyond
  moving Firebase behind a loader.
